# Fool4School 系统不变项

这份文档只写长期不变的系统规律，不绑定某个临时实现。

## 1. 核心目标

系统始终同时服务两件事：

1. 用户现在就拿到自己要的 PDF。
2. 系统逐步把教材沉淀成可复用的正式库存。

这两件事可以互相帮助，但不能混为一件事。

## 2. 资产分层

系统里始终存在三类资产：

1. 临时资产
   贡献者刚生成、尚未正式入库的文件。
2. 索引或征集信息
   用来表达“系统当前想要什么”或“某本书当前处于怎样的中间状态”。
3. 正式资产
   已经进入正式仓库、所有用户都可稳定读取的内容。

正式资产才是最终真相源。

## 3. 状态机

一本书从系统视角通常只会落在三种主状态之一：

1. `local-only`
   用户可以自己生成，但系统当前不主动征集，也还没有正式资产。
2. `solicited`
   系统主动希望它进入正式库存，因此会给出额外入口或提示。
3. `published`
   正式资产已经进入仓库，可稳定读取。

其他更细的状态都应被视为内部实现细节。

## 4. 用户交付与系统物流必须分离

用户要的是“这次下载结果”。
系统要的是“长期可复用库存”。

因此始终应遵守：

1. 用户交付逻辑
   当前这次应该给用户什么 PDF。
2. 系统物流逻辑
   当前这次应该如何补库、登记、发布。

两者可以共用一次计算结果，但产品上不能让用户承担系统物流的复杂性。

## 5. 首次贡献的完整性原则

只要一份贡献要进入长期库存，它就必须足够完整，不能留下结构性错位。

这意味着：

1. 页码映射必须可恢复。
2. 前后置页（例如 `u1/u2/u3`）不能无声丢失。
3. 目录结构不能在首次入库时天然断裂。

换句话说：长期库存需要完整书结构，而不是只保留用户当次想下载的局部范围。

## 6. 正式仓库与临时通道职责不同

正式仓库负责：

1. 稳定读取
2. 长期保存
3. 面向所有用户的统一分发

临时通道负责：

1. 临时接货
2. 等待编排器处理
3. 支撑中间过渡流程

临时通道不能被当成正式仓库。

## 7. 索引层必须存在

如果系统想让“哪些书值得额外处理”被所有客户端一致理解，就必须存在一个可公开读取的索引层。

没有这个索引层，就无法优雅表达“征集什么”“中间状态是什么”“客户端该不该给特殊入口”。

注意：

1. 临时文件存储不是索引层。
2. 通知流不是索引层。
3. 正式仓库也不是索引层。

索引层只负责回答：

1. 这本书是否值得额外处理。
2. 客户端是否应该给特殊入口。
3. 如果有中间状态，它大致处于哪一步。

## 8. 发布动作必须由可信编排器完成

无论前端贡献流程多自动，最终把内容纳入正式仓库的动作，都必须由一个可验证、可校验的编排器完成。

编排器至少负责：

1. 拉取待处理记录
2. 下载临时资产
3. 结构校验
4. 正式入库
5. 清理或更新状态

## 9. 任何外部输入都不可信

以下输入都必须经过校验：

1. 临时上传链接
2. 待处理索引中的记录
3. 通知渠道中的内容
4. 用户端生成的任何附加信息

系统不能因为“有人传了”就默认它可以正式发布。

## 10. 文案原则

用户文案只讲用户能理解和关心的事：

1. 现在会拿到什么
2. 现在正在做什么
3. 失败后该怎么办

用户文案不应暴露：

1. 元数据文件名
2. 仓库内部结构
3. 页码对齐哲学
4. 后厨同步细节

## 11. 演进方向

无论实现细节怎么变化，系统都应朝这条路径演进：

1. 用户交付更简单
2. 征集与中间状态更可见
3. 正式发布更自动
4. 临时层职责更小
5. 正式仓库更稳定
