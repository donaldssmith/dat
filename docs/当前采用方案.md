# Fool4School 当前采用方案

这份文档只记录“现在真正采用的版本”。
如果之后再改路线，只改这份，不改《系统不变项》。

## 1. 当前总结构

当前系统按五层理解：

1. 用户脚本
   文件：`app/userscripts/V14.user.js`
2. 征集清单
   文件：`dist/-1.dat`
3. 临时上传通道
   当前采用：`temp.sh` 主传，`litterbox` 备用
4. 通知通道
   当前采用：Discord webhook + `F4S_JOB` 结构化任务协议
5. 正式仓库与部署器
   当前采用：Hugging Face `dist/<bookId>/` 主分发 + GitHub 后备基础设施 + `app/tools/切分部署台.py`

## 2. 当前正式仓库结构

当前正式仓库仍然以单页切片为核心。

当前分发层采用双轨：

1. Hugging Face
   作为主分发与主发布目标
2. GitHub
   保留原有仓库结构与读取逻辑，作为后备基础设施

也就是说：

1. 客户端优先从 Hugging Face 读取
2. 如果 Hugging Face 暂时抽风，再退回 GitHub
3. 部署器默认只发 Hugging Face
4. GitHub 默认被阻断，不参与日常发布，但结构不拆
正式资产目录本身不变：

1. `dist/<bookId>/1.dat ... N.dat`
   正式单页资产
2. `dist/<bookId>/0.dat`
   书级元数据
3. `dist/-1.dat`
   当前希望大家补进书库的教材清单

其中：

1. `0.dat` 面向机器
2. `-1.dat` 面向“征集哪些书”
3. 用户文案不直接暴露这些文件名

## 3. 当前用户脚本策略

### 3.1 已入库书

如果书已经在正式仓库中：

1. 用户输入看到的页码范围
2. 右侧主按钮直接下载对应 PDF
3. 如果仓库缺少 `0.dat`，脚本会后台顺手补齐

### 3.2 未入库且不在征集清单里

如果书还没入库，但也不在 `-1.dat` 里：

1. 用户仍然可以直接下载自己输入范围的 PDF
2. 这次只做本地生成
3. 不自动上传
4. 不把复杂后厨状态暴露给用户

### 3.3 未入库且在征集清单里

如果书没入库，但命中了 `-1.dat`：

1. 主按钮仍然只负责下载当前输入范围
2. 底部扩展条额外出现“补进书库”
3. 只有用户主动点“补进书库”，才会按整本处理并上传

也就是说：

1. 下载是默认动作
2. 贡献是可选动作
3. 征集只影响“是否展示贡献入口”，不阻止用户先拿自己的 PDF

## 4. 当前 `-1.dat` 约定

当前 `dist/-1.dat` 采用 JSON：

```json
{
  "version": 1,
  "wantedBooks": []
}
```

`wantedBooks` 支持三种写法：

1. 纯字符串

```json
{
  "wantedBooks": ["15809", "6505"]
}
```

2. 简单对象

```json
{
  "wantedBooks": [
    { "bookId": "15809", "title": "Lösungswege Mathematik Oberstufe 7" }
  ]
}
```

3. 带附加字段的对象

```json
{
  "wantedBooks": [
    {
      "bookId": "15809",
      "title": "Lösungswege Mathematik Oberstufe 7",
      "note": "需要整本补库",
      "priority": "high"
    }
  ]
}
```

脚本当前只强依赖：

1. `bookId`

其余字段只是给 UI 更好看，不是硬依赖。

## 5. 当前贡献物流

当用户主动点“补进书库”时：

1. 脚本按整本渲染
2. 本地先把整本 PDF 交给用户
3. 再上传 PDF 临时件
4. 再上传 `0.dat`
5. 最后向 Discord webhook 发通知

当前通知不再依赖自然语言解析，而是统一发送 `F4S_JOB v1`。

任务类型只有四种：

1. `full_upload`
   整本 PDF + `0.dat`
2. `meta_upload`
   只补 `0.dat`
3. `nudge`
   催维护，不带正式入库资产
4. `inventory_signal`
   用户书架里发现“云端没有”的普通教材，只上报线索

部署台只解析结构化任务，不再猜文案。

另外，在书架页扫描阶段，如果脚本发现：

1. 这本普通教材在用户书架里
2. 云端没有
3. 当前也不在 `-1.dat`

就会自动发一条 `inventory_signal` 给维护者，方便后续手动决定是否加入征集清单。

`inventory_signal` 当前只带最小必要信息：

1. `bookId`
2. 标题
3. 本地随机安装别名
4. 可选自定义名字
5. 语言与时区

不上传账号、cookie 或浏览器指纹。

## 6. 当前大文件策略

当前脚本已经不再强行一次性上传超大 PDF。

策略是：

1. 小 PDF 直接上传
2. 大 PDF 自动切片上传
3. 生成 `pdf.parts.json` manifest
4. 通知里给 manifest 链接

这样做是为了绕开前端桥接体积限制。

## 7. 当前页码与目录策略

当前脚本优先依赖：

1. `#thumbnailPanel`
   作为显示页码到机器页的主映射
2. `meta[name="pageLabels"]`
   作为回退
3. `#outlinePanel`
   作为目录树来源

当前实际策略是：

1. 本地下载时尊重用户看到的页码范围
2. 主动补库时按整本处理
3. `u1/u2/u3` 和目录一并保留，避免以后云端错位

## 8. 当前部署器职责

`app/tools/切分部署台.py` 当前仍负责：

1. 读取本地 PDF
2. 切分为 `dist/<bookId>/`
3. 生成正式单页资产
4. 部署进正式仓库
5. 读取 Discord 中的 `F4S_JOB` 任务
6. 按任务类型处理整本补库、元数据补齐、催维护提醒或缺书线索

它当前的发布策略是：

1. 主目标是 Hugging Face
2. GitHub 仍保留在配置里
3. 但 GitHub 默认带“阻断石头”，不会被日常部署误触发
4. 如果以后决定恢复 GitHub 发布，只需要改部署配置，不需要重写脚本和部署器

它现在还没有直接消费 `-1.dat`。

当前 `-1.dat` 的主要作用是：

1. 给前端脚本一个“哪些书值得弹出补库入口”的公开清单

## 9. 当前用户体验哲学

当前产品层遵守这几个原则：

1. 最常见动作永远是下载，而不是贡献
2. 贡献入口只在命中征集清单时出现
3. 用户可以完全不理解仓库结构，也能正常使用
4. 用户拿自己的 PDF，不应该被后厨同步阻塞

## 10. 当前已知边界

当前方案仍然有这些边界：

1. `-1.dat` 只是征集清单，不是待处理状态源
2. 仓库尚未自动记录“谁已经提交过但还没正式发布”
3. Discord 目前只是通知流，不是状态数据库
4. 部署器和用户脚本之间还没有完全自动闭环

## 11. 当前下一步最合理方向

如果继续沿这条路走，最顺的顺序是：

1. 把 `-1.dat` 维护顺手
2. 让贡献文案继续更自然
3. 给部署器补“接收临时资产并正式入库”的流畅体验
4. 再决定要不要新增一个真正的待处理状态层
