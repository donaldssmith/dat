# Fool4School 当前采用方案

这份文档只记录“现在真正采用的版本”。
如果之后再改路线，只改这份，不改《系统不变项》。

## 1. 当前总结构

当前系统按六层理解：

1. 用户脚本
   文件：`app/userscripts/V14.user.js`
2. 征集清单
   文件：`dist/-1.dat`
3. 临时上传通道
   当前采用：`temp.sh` 主传，`litterbox` 备用
4. 任务提交通道
   当前采用：后端 `POST /api/jobs`，或 Discord webhook 作为兼容入口；两者都提交同一份 `F4S_JOB v1`
5. 本地任务队列
   当前采用：`.f4s/jobs.json`，由 `app/backend/store.py` 负责幂等、领取和状态持久化
6. worker 与正式仓库
   当前采用：`app/backend/worker.py` 处理队列，复用 `app/tools/切分部署台.py` 完成切分和发布；Hugging Face `dist/<bookId>/` 为主分发，GitHub 为后备基础设施

## 2. 当前正式仓库结构

当前正式仓库仍然以单页切片为核心。

当前分发层采用双轨：

1. Hugging Face
   作为主分发与主发布目标
2. GitHub
   保留原有仓库结构与读取逻辑，作为后备基础设施

也就是说：

1. 客户端优先从 Hugging Face 读取
2. 如果 Hugging Face 暂时抽风，再退回 GitHub
3. 部署器默认只发 Hugging Face
4. GitHub 默认被阻断，不参与日常发布，但结构不拆
正式资产目录本身不变：

1. `dist/<bookId>/1.dat ... N.dat`
   正式单页资产
2. `dist/<bookId>/0.dat`
   书级元数据
3. `dist/-1.dat`
   当前希望大家补进书库的教材清单

其中：

1. `0.dat` 面向机器
2. `-1.dat` 面向“征集哪些书”
3. 用户文案不直接暴露这些文件名

## 3. 当前用户脚本策略

### 3.1 已入库书

如果书已经在正式仓库中：

1. 用户输入看到的页码范围
2. 右侧主按钮直接下载对应 PDF
3. 如果仓库缺少 `0.dat`，脚本会后台顺手补齐

### 3.2 未入库且不在征集清单里

如果书还没入库，但也不在 `-1.dat` 里：

1. 用户仍然可以直接下载自己输入范围的 PDF
2. 这次只做本地生成
3. 不自动上传
4. 不把复杂后厨状态暴露给用户

### 3.3 未入库且在征集清单里

如果书没入库，但命中了 `-1.dat`：

1. 主按钮仍然只负责下载当前输入范围
2. 底部扩展条额外出现“补进书库”
3. 只有用户主动点“补进书库”，才会按整本处理并上传

也就是说：

1. 下载是默认动作
2. 贡献是可选动作
3. 征集只影响“是否展示贡献入口”，不阻止用户先拿自己的 PDF

## 4. 当前 `-1.dat` 约定

当前 `dist/-1.dat` 采用 JSON：

```json
{
  "version": 1,
  "wantedBooks": []
}
```

`wantedBooks` 支持三种写法：

1. 纯字符串

```json
{
  "wantedBooks": ["15809", "6505"]
}
```

2. 简单对象

```json
{
  "wantedBooks": [
    { "bookId": "15809", "title": "Lösungswege Mathematik Oberstufe 7" }
  ]
}
```

3. 带附加字段的对象

```json
{
  "wantedBooks": [
    {
      "bookId": "15809",
      "title": "Lösungswege Mathematik Oberstufe 7",
      "note": "需要整本补库",
      "priority": "high"
    }
  ]
}
```

脚本当前只强依赖：

1. `bookId`

其余字段只是给 UI 更好看，不是硬依赖。

## 5. 当前贡献物流与任务入队

当用户主动点“补进书库”时：

1. 脚本按整本渲染
2. 本地先把整本 PDF 交给用户
3. 再上传 PDF 临时件
4. 再上传 `0.dat`
5. 生成一条 `F4S_JOB v1`
6. 如果配置了 `BACKEND_JOB_URL`，脚本直接提交到后端；否则发送到 Discord webhook，由 worker 收件器轮询导入

当前通知不再依赖自然语言解析，而是统一发送 `F4S_JOB v1`。

任务类型只有四种：

1. `full_upload`
   整本 PDF + `0.dat`
2. `meta_upload`
   只补 `0.dat`
3. `nudge`
   催维护，不带正式入库资产
4. `inventory_signal`
   用户书架里发现“云端没有”的普通教材，只上报线索

后端和 Discord 收件器只解析结构化任务，不再猜人类文案。Discord 只是运输入口，正式任务会统一进入 `.f4s/jobs.json`。

任务进入队列后的状态流转为：

1. `pending`：已接收，等待 worker 领取
2. `processing`：worker 正在下载、切分或发布
3. `succeeded`：处理完成；如果任务来自 Discord，同时记录消息 ID 为已处理，配置开启时删除原消息
4. `failed`：处理失败，保留错误信息；使用 `python run.py worker --retry-failed` 才会重新入队

成功确认和删除动作发生在任务处理完成之后。临时链接过期、元数据下载失败等错误会留在 `failed`，不会因为轮询自动无限重试。

另外，在书架页扫描阶段，如果脚本发现：

1. 这本普通教材在用户书架里
2. 云端没有
3. 当前也不在 `-1.dat`

就会自动发一条 `inventory_signal` 给维护者，方便后续手动决定是否加入征集清单。

`inventory_signal` 当前只带最小必要信息：

1. `bookId`
2. 标题
3. 本地随机安装别名
4. 可选自定义名字
5. 语言与时区

不上传账号、cookie 或浏览器指纹。

## 6. 当前大文件策略

当前脚本已经不再强行一次性上传超大 PDF。

策略是：

1. 小 PDF 直接上传
2. 大 PDF 自动切片上传
3. 生成 `pdf.parts.json` manifest
4. 通知里给 manifest 链接

这样做是为了绕开前端桥接体积限制。

## 7. 当前页码与目录策略

当前脚本优先依赖：

1. `#thumbnailPanel`
   作为显示页码到机器页的主映射
2. `meta[name="pageLabels"]`
   作为回退
3. `#outlinePanel`
   作为目录树来源

当前实际策略是：

1. 本地下载时尊重用户看到的页码范围
2. 主动补库时按整本处理
3. `u1/u2/u3` 和目录一并保留，避免以后云端错位

## 8. 当前后端与部署器职责

`app/backend/discord.py` 当前负责：

1. 从配置的 Discord 频道拉取消息
2. 提取并校验 `F4S_JOB v1` JSON
3. 以 Discord 消息 ID 做幂等去重
4. 把有效任务写入 `.f4s/jobs.json`

`app/backend/worker.py` 当前负责：

1. 领取 `pending` 任务并记录尝试次数
2. 调用旧部署台的下载、OCR 交接、切分和发布实现
3. 将结果写回 `succeeded` 或 `failed`
4. 成功处理 Discord 任务后更新已处理消息状态，并按配置选择删除原消息

`app/tools/切分部署台.py` 保留正式资产处理和兼容交互入口，仍负责：

1. 读取本地 PDF
2. 切分为 `dist/<bookId>/`
3. 生成正式单页资产
4. 部署进正式仓库
5. 在旧 CLI 中读取和展示 Discord 历史任务
6. 提供 `--discord-cleanup` 历史整理兼容入口
7. 按任务类型处理整本补库、元数据补齐、催维护提醒或缺书线索

它当前的发布策略是：

1. 主目标是 Hugging Face
2. GitHub 仍保留在配置里
3. 但 GitHub 默认带“阻断石头”，不会被日常部署误触发
4. 如果以后决定恢复 GitHub 发布，只需要改部署配置，不需要重写脚本和部署器

当前 `-1.dat` 的主要作用是：

1. 给前端脚本一个“哪些书值得弹出补库入口”的公开清单

## 9. 当前用户体验哲学

当前产品层遵守这几个原则：

1. 最常见动作永远是下载，而不是贡献
2. 贡献入口只在命中征集清单时出现
3. 用户可以完全不理解仓库结构，也能正常使用
4. 用户拿自己的 PDF，不应该被后厨同步阻塞

## 10. 当前已知边界

当前方案仍然有这些边界：

1. `-1.dat` 只是征集清单，不是待处理状态源
2. `.f4s/jobs.json` 是单机 JSON 队列，适合单 worker；不承担多主机并发协调
3. Discord 的已处理消息状态保存在本地配置状态文件；Discord 本身不是任务状态数据库
4. Discord 临时上传链接可能过期，失败任务需要人工确认后使用 `--retry-failed`
5. 成功处理后才会确认或删除 Discord 消息，失败消息会保留以便排查

## 11. 当前运维入口

常用命令：

```powershell
# 导入 Discord 并处理一条任务
python run.py worker --discord-inbox --once

# 持续轮询 Discord 并处理队列
python run.py worker --watch-discord

# 将 failed 任务重新入队后继续处理
python run.py worker --retry-failed
```

Discord 配置位于 `config/local/部署台.bot.json`。`delete_processed_messages` 默认关闭；确认机器人有删除消息权限并完成测试后，再按需开启。
