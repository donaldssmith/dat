  7.2 viewer 分流条件

  - 证据来源文件：
    - EbookPlus 样本 A/DFS-4DWESZ6IGMpage=3.html
    - EbookPlus 样本 B/DFS-VFMPUDAV9Ppage=1.html
    - 两个 app.js
  - 证据位置：
    - 样本 A HTML 第 32-33 行：KlettBrowserRuntime.js + app.js
    - 样本 B HTML 第 26-27 行：css/vendor.css + style.css
    - 样本 B HTML 第 71 行：var settingsJson = "oebv/oebv_ebp_dfs/online";
    - 样本 B HTML 第 73 行：<span id="ep2">...
  - 判断条件：
    - 不是同一套前端实现。样本 A 使用 KlettBrowserRuntime.js（Haxe 3.4 runtime，命名空间
  tink_*/coconut_*/dua_*/xdom_*），样本 B 使用另一套 Haxe runtime（命名空间 pagr_*/dua_*，body class dry scriptable）
    - 样本 A app.js ≈1.1MB，样本 B app.js ≈355KB + vendor/poly.js ≈2.2MB
    - 样本 A 的 settings-json 是自包含的（含 pages、titles、resolutions、thumbs、windows 等完整配置）
    - 样本 B 的 settings-json 是骨架配置（仅含功能开关和 annotation 配置），页面数据来自外部 JSON 文件
  config/oebv/oebv_ebp_dfs/online.json + HTML 预渲染
    - 样本 B 存在 ep2 加密许可检查（样本 A 无）
    - 样本 B 使用 data-pagr-bind 属性绑定（样本 A 无）
    - 两者 productInfo.productForm 相同："oebv_ebp_dfs"
  - 结论：
    - 两种 viewer 是两个独立的前端构建产物，共享同一个产品形态标识（oebv_ebp_dfs），但页面结构、JS
  bundle、数据注入方式均不同
    - 入口差异在服务端渲染阶段已决定：哪个 HTML 模板被下发取决于教材的构建配置（可能是教材出版年份/版本决定，样本 A
  buildYear: "2025"，样本 B data-build-year="2021"）
    - 分流不由浏览器端 JS 运行时判断，而是构建时静态决定

  7.7 最终判断

  已确认可复用的统一点

  1. 页码输入层：两子类型都有 logicalPage 概念（data-pos / titles 数组），且页码标签体系（U1/U2/数字/U3/U4）一致 →
  页码输入 UI 可统一
  2. settings-json 存在：任务书原称两类型"没有显式 settings-json"，实际两个样本都有 <script type="text/settings"
  id="settings-json"> → 配置读取入口可统一于此节点
  3. productInfo 结构：两样本的 productInfo（productForm、productNumber、projectId、appVersion）字段语义一致 →
  产品身份信息可统一提取
  4. annotations 同步配置：两样本的 annotations.sync.server.baseParameter（dienstId、mandant、bookshelfId）结构相同 →
  annotation 接口可统一
  5. 资源 URL 构造模式：都是 content/pages/page_{N}/Scale{1,2,4}.png → 资源路径格式一致
  6. Scale 分辨率体系：都是 Scale1/Scale2/Scale4 三级 → 分辨率选择逻辑可统一

  已确认不能拍脑袋假设的点

  1. 两种 viewer 不是同一套前端实现：代码结构、命名空间、数据注入方式均不同
  2. 样本 A 的 mapping 为 null 不代表所有 img 型书都没有 mapping：当 mapping 存在时 logicalPage ≠ assetIndex
  3. 样本 B 的 title 来自 <title data-original>，不是来自 settings-json.productInfo.title：两样本 title 来源路径不同
  4. 真实 bookId 在 portal 页无法恢复：必须依赖 overview 书架桥接，dienstId/productNumber/projectId 都不是真实编号
  5. 目录/章节源当前不存在于静态 HTML 和 JS 中：不能假设 data.json 一定包含目录
  6. directoryPage 仅样本 A 有（=4），样本 B 没有对应字段

  如果后续继续开发，最先该解决的单一阻塞是什么

  恢复 portal 页的真实 bookId。目前必须靠 GM_setValue 桥接（overview → portal），这在以下场景会断：直接打开 portal
  URL、书签恢复、跨设备同步。如果能在 portal 页通过 settings-json + data.json（或 online.json）反向解析出 thumb/13915
  格式的真实编号，整个 Ebook 与 EbookPlus 的身份语义才能统一。dienstId（DFS
  token）与真实书号的映射关系是当前最大的单点阻塞。
